# Grandfa Farm Cafe & Resort — POS

ระบบ POS หน้าร้านสำหรับ iPad แนวนอน (ใช้ผ่านเว็บเบราว์เซอร์): ขายสินค้า รับเงินสด/เงินโอน ติดตามออเดอร์ที่รอทำ เงินเข้า-ออก เปิด/ปิดกะ รายงาน และจัดการเมนู

**สแตก:** Next.js 15 (App Router) + TypeScript + Tailwind CSS v4 · Supabase (Postgres + Auth + RLS) · Vercel
**เขตเวลา** Asia/Bangkok · **สกุลเงิน** THB (เก็บเป็น "สตางค์" จำนวนเต็มทั้งระบบ ไม่ใช้ float)

## โครงสร้างหน้าจอ

- **ขายสินค้า (/pos)** — 3 คอลัมน์: เมนู (หมวด+ค้นหา+การ์ดสินค้า) · ออเดอร์ปัจจุบัน (+/−, ลบ, ตัวเลือกเสริม, ส่วนลด, ยอดรวม, คิดเงิน) · ออเดอร์ที่ชำระแล้ว (แท็บ "รอทำ"/"เสร็จแล้ว", ปุ่ม DONE, ย้อนกลับพร้อมยืนยัน, ใบเสร็จ)
- **งานผลิต (/production)** — จอครัว (KDS): แยกจอ เค้ก+เครื่องดื่ม / แท็บ เค้ก · เครื่องดื่ม · ทุกออเดอร์ (แต่ละเครื่องเลือกได้เอง `?station=cake|drink|all`), สรุปตัวเลขใหญ่, แผงรอบอบเค้ก, ช่อง "พร้อมส่งมอบ"
- **ติดตามคิว (/q/<token>)** — หน้าสาธารณะสำหรับลูกค้า (สแกน QR) ไม่ต้องล็อกอิน เห็นเฉพาะคิวของตัวเอง
- **ประวัติออเดอร์ (/orders)** — ค้นย้อนหลัง, คืนเงิน (ผู้จัดการขึ้นไป)
- **เงินเข้า-ออก (/cash)** · **รายงาน (/reports)** · **สินค้า (/products)** · **สต็อก (/inventory)** · **พนักงาน (/employees)** · **ลูกค้า (/customers)** · **ตั้งค่า (/settings)** · **ช่วยเหลือ (/help)**
- ใบเสร็จ: `/receipt/<order id>` (ปุ่มพิมพ์ใช้ print ของเบราว์เซอร์)

### บทบาท
| บทบาท | ทำได้ |
|---|---|
| owner (เจ้าของ) | ทุกอย่าง รวมพนักงาน/ตั้งค่า/audit log |
| manager (ผู้จัดการ) | + รายงาน, สินค้า, สต็อก, คืนเงิน, กลับรายการเงินเข้า-ออก |
| cashier (แคชเชียร์) | ขาย, เงินเข้า-ออก, เปิด/ปิดกะ, DONE; เห็นข้อมูล "ของวันนี้" เท่านั้น |

สิทธิ์ถูกตรวจ 3 ชั้น: เมนู/หน้า (UI) → Server Action (zod + role) → ฐานข้อมูล (RLS + ฟังก์ชัน SECURITY DEFINER)

## กติกาทางการเงิน (ใช้ตรงกันทั้งระบบ)

- **ยอดขายรวม (gross)** = Σ ยอดก่อนส่วนลด · **สุทธิ** = ยอดขาย − ส่วนลด − คืนเงิน
- **เงินสดที่ควรมี** = เงินทอนตั้งต้น + ขายเงินสด + เงินสดเข้า − เงินสดออก − คืนเงินสด
- **ส่วนต่าง** = เงินที่นับได้ − เงินสดที่ควรมี
- **เงินโอนไม่เข้าลิ้นชักเงินสด** · รายจ่าย (ช่องทางโอน) ไม่ลดลิ้นชัก, รายจ่ายเงินสดลดลิ้นชัก · รายจ่ายและการคืนเงินไม่นับเป็นยอดขาย
- คืนเงินสด/กลับรายการที่ทำคนละกะ จะหักจากลิ้นชักของ **กะปัจจุบัน** (สรุปกะที่ปิดแล้วไม่ถูกแก้ย้อนหลัง)
- ราคา/ส่วนลด/ยอดรวม **คำนวณที่ฐานข้อมูลเท่านั้น** (client ส่งแค่ product id, จำนวน, ตัวเลือกเสริม) · ชื่อและราคาสินค้าถูกเก็บสำเนาในบิล
- ชำระเงินใช้ `idempotency_key` — กดซ้ำ/เน็ตหลุดแล้วลองใหม่ จะได้ออเดอร์เดิม ไม่ตัดเงินซ้ำ (เช่นเดียวกับคืนเงิน/เงินเข้า-ออก)
- `orders`, `order_items`, `payments`, `refunds`, `cash_movements`, `shifts` (ที่ปิดแล้ว), `audit_logs` **ลบ/แก้ไม่ได้** (trigger) และไม่มีสิทธิ์เขียนตรงจาก API — แก้ผ่านคืนเงิน/กลับรายการ (มีเหตุผลและ audit)
- เงินโอน: ต้องติ๊กยืนยันว่า "เงินเข้าแล้ว" ก่อนกดยืนยัน และยอดต้องเท่ากับยอดบิลพอดี

### เมนูและราคา
- เมนูเริ่มต้น: Basque Burnt Cheesecake (Original ฿59, Matcha ฿79, Red Velvet ฿69) และ Matcha & Tea 6 รายการ
- **เครื่องดื่ม 6 รายการยังไม่มีราคา (NULL)** เพราะข้อความต้นฉบับไม่ระบุชัดว่าราคาไหนเป็นของเมนูไหน — ระบบไม่เดาราคา
- ระบบ **ปิดการขายเป็นค่าเริ่มต้น** (`settings.sales_enabled = false`): เจ้าของต้องตั้งราคา (หรือปิดการใช้งานเมนูที่ไม่ขาย) แล้วเปิดการขายที่หน้า ตั้งค่า — ระบบไม่ให้เปิดถ้ายังมีเมนูที่เปิดใช้งานแต่ไม่มีราคา

## ระบบคิว · งานผลิต · รอบอบเค้ก (เพิ่มใน migration 0004)

เพิ่มแบบ **ต่อยอดของเดิม** — ไม่แก้ checkout/ชำระเงิน/กะ/ภาษี/ใบเสร็จ/รายงาน/RLS เดิม (รายละเอียดดู `docs/COMPATIBILITY.md`)

**การทำงาน**
1. ชำระเงินสำเร็จ → trigger บน `payments` สร้างคิว (เลข Q001… รีเซ็ตทุกวัน, ไม่ซ้ำแม้ขายพร้อมกัน) + token สุ่ม 64 ตัวอักษร; ชำระไม่สำเร็จ = ไม่มีคิว; สร้างคิวพลาดจะไม่ทำให้การขายล้ม (แล้วกด "สร้างคิวให้" ที่หน้างานผลิตได้)
2. แต่ละรายการแยกเป็นงานของสถานี เค้ก/เครื่องดื่ม (ตามหมวด/สินค้า ตั้งค่าได้) — ออเดอร์เป็น "พร้อมรับ" ก็ต่อเมื่อทุกสถานีที่ต้องทำพร้อมแล้ว แล้วพนักงาน "ส่งมอบ" → เสร็จสิ้น (ปุ่ม DONE เดิมที่ POS ใช้ได้ต่อและซิงก์กับคิว)
3. รอบอบเค้ก: ระบบเสนอแผนแบบมาก่อนได้ก่อน (เช่น 28 ชิ้น → 22 + 6) พนักงานกด "ยืนยันแผน" → "เริ่มอบ" → "อบเสร็จ"; เค้กที่เริ่มอบแล้วไม่ถูกย้าย, ปรับด้วยมือได้ก่อนเริ่มอบ, ความจุเริ่มต้น 22 (แก้ได้), ป้องกันจัดเกินความจุใน transaction
4. ลูกค้าสแกน QR (หน้าสำเร็จหลังชำระ / ใบเสร็จ / ปุ่ม QR ที่รายการออเดอร์) → เห็นเลขคิวตัวเอง, จำนวนคิวก่อนหน้า, รายการ, ความคืบหน้าเค้ก/เครื่องดื่ม, สถานะรวม, วิธีรับ; ประเมินเวลาเฉพาะเมื่อร้านตั้ง "เวลาอบต่อรอบ" ไว้ (ไม่มีข้อมูล = ไม่เดา)
5. ปุ่มกดทุกปุ่มกัน "กดซ้ำ" ที่หน้าจอ + ฐานข้อมูลทำงานแบบ idempotent; หน้าจอใช้ SyncController ที่ทิ้งผล polling ที่เก่ากว่าการกดล่าสุด (แก้อาการ DONE ต้องกดหลายครั้ง) ผลทดสอบ: `tests/unit/sync-controller.test.ts`

### ติดตั้ง/อัปเกรด (ต้องทำเอง — **ไม่มีอะไรถูกรันบน production ให้อัตโนมัติ**)
1. สำรองฐานข้อมูล (Supabase → Database → Backups) แล้ว **รัน `supabase/migrations/0004_queue_production.sql` ก่อน** deploy โค้ดใหม่ (SQL Editor หรือ `supabase db push`) — ไฟล์เป็น additive, ไม่แตะข้อมูลการเงิน
2. ตอนรัน 0004 ระบบจะ **เดาสถานีของหมวดจากชื่อหมวด** (ชื่อมี cheesecake/cake/เค้ก/bakery/เบเกอรี่ → เค้ก; matcha/tea/coffee/latte/drink/ชา/กาแฟ/เครื่องดื่ม → เครื่องดื่ม; อื่น ๆ ไม่กำหนด = ใช้ค่าเริ่มต้น "เครื่องดื่ม") — `seed.sql` (รันซ้ำได้) ก็กำหนดหมวดตัวอย่างให้เช่นกัน **ตรวจที่ งานผลิต → ⚙ ตั้งค่า** ว่าหมวด/สินค้าของร้านไปสถานีถูกต้อง (เค้กที่ถูกจัดเป็นเครื่องดื่มจะไม่เข้ารอบอบ)
3. Deploy โค้ดบน Vercel (ไม่มี env ใหม่) แล้วทดสอบตามเช็กลิสต์ด้านล่าง
4. ย้อนกลับ: `supabase/rollback/0004_rollback.sql` (ลบเฉพาะของใหม่; ต้องย้อนโค้ดกลับก่อน) — โค้ด POS ถูกเขียนให้ยังขายได้ถ้ายังไม่ได้รัน 0004 (ส่วนคิวจะไม่แสดง)
5. ออเดอร์ที่ชำระก่อนเปิดใช้ระบบ **ไม่ถูก backfill อัตโนมัติ** — หน้างานผลิตจะแจ้ง "มี N ออเดอร์ที่ยังไม่มีคิว" และมีปุ่มสร้างให้ (เฉพาะออเดอร์ของวันนี้ที่ชำระแล้วและไม่ได้คืนเงิน)
6. Realtime: migration เพิ่มตารางคิวเข้า publication `supabase_realtime` ถ้ามี ถ้าไม่ได้เปิด/ไม่มีสิทธิ์ หน้าจอจะ poll ทุก 5 วินาทีเอง (ลูกค้าใช้ polling เสมอ)

### ข้อสมมติฐานที่ตัดสินใจเอง (แก้ได้)
- สินค้าที่ไม่ได้กำหนดสถานี → "เครื่องดื่ม"; การเดาจากชื่อหมวดทำครั้งเดียวตอนรัน 0004 (แก้ได้ในหน้าตั้งค่า)
- ลิงก์คิวของลูกค้าหมดอายุ 24 ชม. (ตั้งได้ 1–168); ใครมีลิงก์ก็เปิดได้ (bearer token) จึงเปิดเผยเฉพาะเลขคิว/รายการ/สถานะ ไม่มีชื่อ เบอร์ ราคา หรือรหัสภายใน
- แคชเชียร์เห็นคิวของวันนี้เท่านั้น; ผู้จัดการ/เจ้าของเห็นย้อนหลัง
- เลขคิวรีเซ็ตทุกวัน (เวลา Asia/Bangkok) เหมือนเลขออเดอร์
- ออเดอร์ที่คืนเงิน (refunded) → คิวถูกยกเลิกอัตโนมัติ (คืนบางส่วนไม่กระทบคิว)
- ความจุรอบอบเป็นจำนวน "ชิ้น" ไม่แยกขนาด

### เช็กลิสต์ทดสอบคิว/งานผลิตบน iPad จริง (หลังรัน 0004 + deploy)
1. ขายเค้ก+เครื่องดื่ม 1 บิล → หน้าสำเร็จต้องมีเลขคิว+QR; สแกนด้วยมือถือ → เห็นเฉพาะคิวนั้น
2. เปิด `/production?station=drink` บน iPad เครื่องหนึ่ง และ `?station=cake` อีกเครื่อง → ทำงานแยกกัน; กดเริ่ม/พร้อมแล้ว → อีกเครื่อง/หน้าลูกค้าอัปเดตภายในไม่กี่วินาที
3. ขายเค้กรวม 28 ชิ้น → แผนต้องเป็น 22 + 6 → ยืนยันแผน → เริ่มอบรอบแรก → ขายเค้กเพิ่ม ต้องไม่เข้ารอบที่กำลังอบ
4. กด "พร้อมแล้ว" ให้ครบทุกสถานี → ขึ้น "พร้อมรับ" → ส่งมอบ → ลูกค้าเห็น "รับสินค้าแล้ว" และหน้าหยุดโหลด
5. ที่ POS กด DONE รัว ๆ ต้องเปลี่ยนสถานะ 1 ครั้งและไม่เด้งกลับ; ปิดเน็ตสั้น ๆ แล้วกด → แจ้งผิดพลาด ไม่ค้าง
6. คืนเงินบิลหนึ่ง → คิวนั้นต้องถูกยกเลิก; ลิงก์ของคิวเก่าเกิน 24 ชม. ต้องแสดง "ลิงก์หมดอายุ"

1. สร้างโปรเจกต์ที่ supabase.com
2. **Authentication → Providers → Email**: ปิด "Allow new users to sign up" (บัญชีพนักงานสร้างโดยเจ้าของในแอปเท่านั้น)
3. รัน SQL ตามลำดับ (SQL Editor หรือ `supabase db push`):
   `supabase/migrations/0001_schema.sql` → `0002_functions.sql` → `0003_rls.sql`
   แล้วรัน `supabase/seed.sql` (รันซ้ำได้ ไม่สร้างข้อมูลซ้ำ)
4. **Authentication → Users → Add user** สร้างบัญชีแรกของเจ้าของร้าน (ใส่ Auto Confirm) — **คนแรกที่ถูกสร้างจะเป็น owner อัตโนมัติ** (หลังจากนั้นสร้างพนักงานอื่นในหน้า "พนักงาน")
5. คัดลอกจาก Project Settings → API: Project URL, anon/publishable key, service_role key

> บัญชีที่สมัครเองโดยไม่ผ่านเจ้าของจะถูกสร้างแบบ "ปิดใช้งาน" และการใส่ `role` ใน user_metadata ไม่มีผล (trigger อ่านบทบาทจาก `app_metadata` ซึ่งตั้งได้เฉพาะ service role)

### 2) รันในเครื่อง
```bash
cp .env.example .env.local      # ใส่ค่า 3 ตัว
npm install
npm run typecheck && npm test
npm run dev                     # http://localhost:3000
```

### 3) Deploy บน Vercel
1. push โค้ดขึ้น GitHub → Vercel → Add New Project → เลือก repo (Framework: Next.js)
2. Environment Variables (Production + Preview):
   - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY` — **ห้ามติ๊ก expose / ห้ามมี NEXT_PUBLIC_** (ใช้เฉพาะ `src/lib/supabase/admin.ts` ฝั่งเซิร์ฟเวอร์สำหรับสร้างบัญชีพนักงาน)
3. Deploy แล้วเปิดบน iPad → Share → **Add to Home Screen** (เต็มจอ)
4. Supabase → Authentication → URL Configuration: ใส่โดเมน Vercel เป็น Site URL

## เช็กลิสต์ทดสอบหลัง deploy (ทำบน iPad จริง)
1. ล็อกอินเจ้าของ → หน้า สินค้า ตั้งราคาเครื่องดื่มที่ถูกต้อง → ตั้งค่า → เปิดการขาย
2. สร้างพนักงานแคชเชียร์ ล็อกอินด้วยบัญชีนั้น (ต้องไม่เห็นเมนูรายงาน/สินค้า/พนักงาน/ตั้งค่า และเข้า `/reports` ไม่ได้)
3. เปิดกะ ฿1,000 → ขาย (เงินสด 1 บิล, โอน 1 บิล, มีส่วนลด 1 บิล) → กด DONE → ย้อนกลับ → DONE
4. กด "ยืนยันรับชำระ" รัว ๆ / ปิดเน็ตชั่วคราวแล้วกดซ้ำ → ต้องได้บิลเดียว
5. เงินเข้า-ออก: เงินสดออก ฿100 (ลิ้นชักลด), โอนออก ฿100 (ลิ้นชักไม่ลด)
6. ผู้จัดการคืนเงินบิลหนึ่ง → ตรวจสรุปกะและรายงานว่าไม่นับซ้ำ
7. ปิดกะ ใส่เงินนับได้ไม่ตรง → ตรวจส่วนต่าง → ยืนยัน → เปิดสรุปกะเก่าต้องไม่เปลี่ยน
8. พิมพ์ใบเสร็จจากเบราว์เซอร์

## ข้อจำกัดที่ตั้งใจไว้
- (คิว/งานผลิต) ไม่มี: ล็อกอินลูกค้า, แจ้งเตือน LINE/SMS/push, สัญญาเวลารับที่แน่นอน (ประเมินเฉพาะเมื่อมี "เวลาอบต่อรอบ"), ระบบสต็อกวัตถุดิบ; หน้าลูกค้าใช้ polling (5–30 วินาที) ไม่ใช้ Realtime
- (คิว/งานผลิต) ใครมีลิงก์คิวก็เปิดได้จนหมดอายุ — ถ้าสงสัยว่ารั่วให้ลดอายุลิงก์ที่ตั้งค่า; ไม่มีปุ่ม "เปลี่ยน token" ในเวอร์ชันนี้
- ตะกร้าที่ยังไม่ชำระอยู่ในหน้าจอเครื่องนั้น (ไม่เก็บลงฐานข้อมูล) — รีเฟรชหน้าตะกร้าจะหาย; ออเดอร์เกิดในฐานข้อมูลตอนชำระเงินเท่านั้น (เลขออเดอร์ #001 รีเซ็ตทุกวัน)
- รองรับเครื่อง POS 1 เครื่อง/ลิ้นชัก (ตาราง `registers` รองรับหลายเครื่อง แต่ UI เลือกเครื่องแรก)
- คืนเงินเป็นรายออเดอร์/จำนวนเงิน (ยังไม่แยกรายชิ้นหรือคืนสต็อกอัตโนมัติ)
- การตัดสต็อกยอมให้ติดลบได้ (ไม่บล็อกการขาย) และแจ้งสีแดงในหน้า สต็อก
- เบราว์เซอร์ iPad ต้องออนไลน์ตลอด (ไม่มีโหมดออฟไลน์)
